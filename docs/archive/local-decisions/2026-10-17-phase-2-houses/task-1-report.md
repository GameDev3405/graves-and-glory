### Preflight (`tools/preflight.py`, one block before `if errors:`)
Until Task 2 adds `troops.house` and `troops.rarity`, a troop's House and rarity are derived from its position in `houses.troops`.
- **rarities and houses:**
  - the rarities rows are exactly common, rare, epic and legendary;
  - each House has the glyph path `gravesandglory:textures/gui/house/<id>.png` and lists 6 troops;
  - no troop sits in two Houses.
- **houseTraits:**
  - tiers are exactly 1 to 3 per House, with one mechanic per House and rising slots;
  - the house resolves and the id is `<house>_<tier>`.
- **abilities:**
  - mechanic and trigger come from the closed lists, and target is enemies or allies;
  - stance rows have amount 0;
  - text is 90 characters or fewer.
- **counters:**
  - the condition comes from the closed list, and every tag resolves (dynamic tags, the spec section 3 troop tags, ability ids);
  - `replaces` is `none` or a `|` list of other counter ids;
  - the multiplier is above 0.
- **combatDiscipline:** `0 < multiplierMin <= 1 <= multiplierMax`.
- **recruitment and campaign:** recruitment has one row; the four campaign House reward amounts are 0 or more.
- **rarities:**
  - star bonuses rise and stay within `capPct`;
  - `slotWeight` and `bannerMax` are at least 1.
- **evolutions:**
  - the id is `<troop>_<stage>` for stage 2 or 3;
  - only a House Common or Rare evolves;
  - the hard cap holds: `starPct3 + max(healthPct, damagePct) <= capPct`;
  - every Common and Rare has stages 2 and 3, and stage 3 is not below stage 2.
- **mastery and renown:**
  - levels run 1..n, and thresholds rise;
  - the `legendary` renown row sits at `recruitment.renownForLegendary`.
- **botBanners:**
  - house and difficulty resolve, and the id format holds (a mixed id names the first House in `house`);
  - each banner has `rules.squadSize` entries;
  - every `^` follows its unit, with none missing and none orphaned;
  - troops belong to the banner's Houses;
  - slot weights sum to the squad size, and the `bannerMax` limits hold.

## Brief vs spec, and other deviations
1. **Gilded accent: 14667368 (brief), not 14667624 (spec 6.1 example).** The spec's own colour is hex 0xDFCE68, which is 14667368; its int is 0xDFCF68. The brief's value matches the spec's stated colour (plan Spec gaps 10).
2. **ic_ballista uses the striker pattern (brief), not the spec's +3/+3 then +2/+4.** The spec's row breaks the spec's own hard cap (4.4: star 3 + stage <= +12%, which "a standalone check asserts for every row"). Following the spec's cap rule gives the brief's answer (plan Spec gaps 6); the names are kept.
3. **C7 attacker is `cavalry` (brief); the spec says "`beast` or `cavalry`".** These are equivalent: spec section 3 lists "beast and cavalry" on the same four troops (wm_hound, wm_stalker, wm_oldhorn, tc_brute).
4. **Extra columns resolve plan-documented spec gaps, not conflicts.** `houses.fieldable`, `houseTraits.value2`, `abilities.trigger`/`amount2` and `combatDiscipline.multiplierMin`/`Max` are plan Spec gaps 3 and 4.
5. **`economy.refundGold` (300).** Brief Step 5 names it; spec 6.3 says "refund 300 gold" without naming a column.
6. **New: `campaign.completionShards`, `victoryShards`, `completionRenown`, `victoryRenown` (1 each).** This is my addition, to honour "no ... reward number hard-coded in Java". The brief's `matchRewards` signature takes no amounts, and the brief fixes the recruitment row exactly. So the spec 4.3 and 4.5 amounts sit beside `completionGold` and `victoryGold`, which `Campaign` already pays per eligible match and per win. `matchRewards` keeps the brief's signature and reads them from Spec. 8. **The cap loop in HousesCheck uses each troop's own rarity row** instead of `rarity("common")`, and is null-safe. The numbers are identical today (Common and Rare starPct3 are both 0.06), and the check is stricter if they ever diverge.

3. **Constants still in Java:**
   - `starterBanner()`: knight x12, then archer to `squadSize`, as the brief specifies.
   - `CounterMath.FRONT_DEGREES = 90`: the brief's "front means bearing <= 90", the vanilla shield half-plane. Flank reads `morale.flankArcDegrees`.

4. **Preflight placeholders for Task 2.** The counter troop-tag list (shield, spear, beast, cavalry, siege, large, small, fearless) is hard-coded, and `POSITION_RARITY` derives House and rarity from `houses.troops`. When Task 2 adds `troops.tags`, `house` and `rarity`, it should switch both to the troop columns.
5. **Semantics I chose where the brief is silent:**
   - An orphan `^` counts for nothing in `houseSlots`.
   - A dismantle at max stars does not increment `copies`.
   - The win shard bonus goes to the largest House only when it is at tier I or higher. A banner with no tier-I House earns nothing, even on a win; ties go to the first in House order.
   - `sanitize` repacks a fully invalid banner to all `empty`; it does not fall back to `starterBanner()`.
   - `upgradeFile` writes the `.v1.json` backup before the temp file, so a failed temp write leaves a harmless backup and the original untouched.
6. **Call `upgradeFile` only on `<uuid>.json`.** Run on a `<uuid>.v1.json` it would produce `<uuid>.v1.v1.json`. `Campaign.profile` resolves `key + ".json"`, so the natural call site is fine.
7. **Preflight's new rules index columns directly,** as the Phase 1 rules do. A column renamed on every row gives a KeyError traceback instead of a message, which is the existing behaviour.
8. **`docs/PARKED.md` got a new section at the end.** The main worktree has uncommitted `PARKED.md` edits, so a later merge may need both sections kept.
