## 1. Animation spec draft (M3)

**Goal.** Troops look distinct and alive in the six classes. The code clip system already exists (18 clips per rig; `TroopAnimator` blends by state and stance). Pass 1 fills the gaps only.

**Pass 1 builds**
- Six classes, core states: idle, walk, run, hit, death. Audit which of the 18 existing clips already read well; fix only the weak ones.
- Weapon-specific attack swings, by code clips: sword, axe, spear (thrust), trident. Mace is in the plan's gap list; [A] mace and bow ride along only if a class needs them.
- Charge: a leaned `run` variant with the weapon forward (the `order=charge` already exists server side).
- Formation march: a `walk` variant. Marching "with teammates" (rank awareness) is pass 2.

**Blender-keyed (hand-made)**
- Only the one or two signature attacks per class, and the charge if the code version looks flat.
- Needs one import format: Blockbench/Blender into the mod's `Animation` data. `TroopClips` builds clips only in code today, so a loader is the first piece of work.

**Effort (no dates)**
- Audit and contact-sheet harness setup: S
- Four attack variants plus charge and march in code: M
- Blender import path and signature clips: L (depends on who keys them)
- Review rounds to threshold 9: M

**Files likely touched**
- `src/main/java/gg/gravesandglory/TroopClips.java` (and `BipedClips` for the biped rig)
- `src/main/java/gg/gravesandglory/TroopAnimator.java` (state selection, charge and march blend)
- `src/main/java/gg/gravesandglory/TroopTells.java` (per-House attack variants must keep working)
- A new clip loader if Blender clips are used. Client-only; no server code.

**Tests**
- Contact sheets per class and state via the existing harness (`shotTime`), at threshold 9 per `WORKFLOW.md`.
- No regression in `TroopTells` idle tells or left-handed mirroring.
- Clip data checks (all required clips present per rig) in `test-tools/`.
- Proof that server hit timing is unchanged. A timing change is a gameplay change.
- One real-game look by Kort at the end; headless bots do not count.

**Open decisions**
1. What "all 6 classes" means. [A] the six troop classes, since the existing rigs serve them. If it means the six commander classes, player-model animation likely needs a new mixin or dependency, which is a dependency decision.
2. Who keys the Blender clips: Claude, Kort or the builder. [A] Claude does the code clips; Blender is Kort's or the builder's call.
3. May pass 2 add stance or formation data to the protocol? That is a protocol change. Pass 1 needs none ([A]: `stance_v1` already carries what it needs).

## 2. Map-adoption spec draft (M5)

**Goal.** Finished builder worlds (camp, rivergate, ironhold, frostmarch, hollowwood, kingsfield) become the real maps. They live on the builder server (`BUILDER-SERVER.md`); each world's builds are saved in `gg-build-<world>`.

**What changes**
- Bypass generation: today Arena heights, the camp terrain hash, the landmark queue and height pass, and the box-diff rule build the map. An adopted map loads as saved instead of generating. [A] a per-map flag in `sheets/design.json` selects "adopted".
- Re-derive or keep the gameplay data tied to layout: spawns, capture circles, routes, landmark rows, cover and sight lines. [A] a scan tool reads the adopted world and proposes new values; the builder and Kort confirm moved points.
- `CampTerrain.REVISION` (in `CampTerrain.java`): bump so camps rebuild once. Camp stations in `sheets/design.json` (campStations/campPieces) move to the builder's layout. Spec.java stays generated by `tools/preflight.py`.

**How saves ship (decision needed)**
- A: structure files baked into the jar. Small, versioned, reviewable; loses terrain unless exported as large structures.
- B: world data (the saved worlds) bundled with the mod. Exact copy of what the builder made; large, and the BuildMode `gg-build.json` marker must be handled.
- [A] recommend A for buildings and B for terrain only if A cannot hold the terrain. Decide after the builder's worlds exist.

**Approval gates** (all need Kort)
- The adoption design: replacing generation, how saves ship.
- Each world declared "done" by Kort and the builder.
- Any moved spawn or capture point.
- Screenshots of each adopted map and the camp.

**Tests**
- Walk and route suites per map (`test-tools/java/gg/gravesandglory/Walkability.java` and the routes checks) rerun on each edited map.
- Bots path and capture on each map.
- Camp stations reachable; `test-tools/standalone/CampTerrainCheck.java` updated for the new revision.
- Save/load: an old save either migrates or is declared unsupported (needs a decision).
- Real-client look, not headless only.

**Screenshots to approve:** one overview and one lane view per map; camp hearth/gates/stations; each capture circle and spawn at normal and small window sizes.
