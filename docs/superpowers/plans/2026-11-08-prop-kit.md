# Prop Kit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Large, living, multi-block props (the blacksmith forge and smithy set) that builders place from a menu on the builder server and that survive export into battle maps and the Old Hold hub, with no client registry entries.

**Architecture:** A prop is data (a JSON def in the jar's data pack plus item models in a server resource pack keyed by `custom_model_data` on `minecraft:paper`). In the world it is a vanilla jigsaw block (the anchor, carrying id and facing) under the prop, `barrier`/`light` blocks over its footprint, and tagged `item_display` entities that a scanner respawns from anchors. A proximity-gated ticker plays vanilla particles and sounds.

**Tech Stack:** Minecraft 1.20.1 Fabric (Loader 0.16.14, API 0.92.2+1.20.1, Yarn 1.20.1+build.10), Java 17, Python 3.12 (stdlib + Pillow for sheets), Blockbench (Java item model format).

**Spec:** `docs/superpowers/specs/2026-11-08-prop-kit-design.md` (Kort approved 2026-11-08). Policy: `docs/WORKFLOW.md`.

## Global Constraints

- No registry entries: "no custom blocks, block-entity types or items". No `Registry.register` in any prop code; sounds and particles are vanilla ids only.
- Art: "chunky 16 px-per-block pixel textures" (1 texel per model pixel, troop palette approach, one texture sheet per prop).
- A single item model's elements stay inside -16..32 (3 blocks); larger props split into parts.
- Effects run only when a player is within about 24 blocks (`Props.RANGE = 24.0`).
- Prop removal and placement need op level 2.
- Base: branch both tracks from current `main` (0.5.1). One writer per checkout: ART in worktree `prop-kit-art`, SYSTEMS in `prop-kit-systems`.
- After the one jar + builder-pack update, a new prop needs only a new server resource pack (plus its data def; never a client jar).
- Workers (WORKFLOW 2026-11-07): Opus 5.5 medium for art, UI and systems tasks; Sonnet 5.5 high for checks, fixes and reviews; never Fable; xhigh only if a task says so. At most two automatic fix rounds.
- No push, publish or merge under this plan. Battle solidity (S9) is gameplay: Kort signs off in game before that branch merges.
- `custom_model_data` range for props: `7310001..7310999` on `minecraft:paper` (S2 checks it clashes with nothing in armory, weapons or `dependencies/resourcepacks/Excalibur_V1.20.zip`).

## Review Focus

1. Placing a prop where its footprint overlaps non-air blocks or another prop: refused with a chat message naming the blocking cell, nothing changed (S4 test `refusesOverlap`).
2. Server restart or chunk reload: display entities are persisted *and* the scanner runs; there must never be two copies (S4 scanner dedupes by tag `gg_prop@x,y,z`; in-game step restarts the server and counts entities).
3. Anchor erased by WorldEdit/Axiom/Ledger rollback: orphan display entities vanish on the next scan; a pasted copy with anchors gets its entities (S4, S8 in-game steps).
4. A structure placed at 90/180/270: every prop faces and sits where it was relative to the structure (S3 composition check, S8 in-game rotated placement).
5. Vanilla client declines the pack: the builder server requires it, so the client is told why and disconnected cleanly, not left seeing paper items (S7 in-game step).

## Design gaps found while planning

- **Vanilla clients and registry sync:** G&G registers its own entries; whether a vanilla client can join the build-mode server at all is unverified. S1e checks it; if it fails, acceptance item 2 is blocked by PLAIN-1, not by props.
- **Pack hosting:** the builder host exposes only the game port today; serving the pack needs one more port or an external HTTPS host. The orchestrator picks (S7/I2).
- **Engine-built maps** (`tools/mapengine` tiles, `EngineMaps.load`) keep only block states, so anchors are dropped there. Out of scope here; builder maps reach the game through mapforge structures/`MapAdoption`, which keep block-entity NBT.
- **mapforge rotation** does not turn the jigsaw `orientation` property today (fixed in S8).
- **"Adding a prop needs only a pack"**: a prop also needs its def; the plan ships defs in a world data pack so no jar change is needed. Kort may want the def inside the resource pack instead (not possible: resource packs are client-side).
